# Game-owned shader materials

Place each descriptor at `materials/<name>/material.json`. Generate with the bgfx backend (the null tests target is also supported). No water/fog/lamp semantics or ECS components are generated by this pipeline.

```json
{
  "version": 1,
  "label": "fog",
  "fragment": "fs_fog.sc",
  "targets": ["spv", "glsl", "essl", "mtl"],
  "parameters": [{"name": "u_tint", "kind": "vec4", "defaults": [1,1,1,1]}],
  "textures": [{"name": "s_noise", "sampler": "linear"}],
  "blend": "alpha"
}
```

`version`, `fragment`, and nonempty `targets` are required. Unknown fields are rejected. Label defaults to the folder name. Parameters/textures default empty, count defaults 1, defaults default empty (core zero-initializes), sampler defaults `point`, blend defaults `alpha`. Kinds: `scalar`, `vec2`, `vec3`, `vec4`, `mat4`; blend: `alpha`, `additive`. Nonempty defaults must have exactly channels × count finite floats. The limits match core contract v2: 16 parameters, 4 extra textures, 64 registers including one reserved for the automatic `u_material_rect`. Matrices use four registers each. Names are ASCII identifiers, maximum 63 bytes. All bindings must be unique, including across parameters and textures. `s_tex`, `u_material_rect`, and BGFX predefined `u_view*`, `u_proj`, `u_inv*`, `u_model*`, `u_alphaRef4` names listed in `material_schema.zig` are reserved.

Folder names are identifiers and must be unique ignoring case. Generated symbols `core`, `sm`, `parameters`, `textures`, `shaders`, `label`, `blend`, `descriptor`, `bindings`, `_` are reserved folder names.

Fragments pair with the existing sprite vertex shader. Inputs are `v_color0` and `v_texcoord0`; the build supplies its fixed sprite `varying.def.sc`. The base sprite texture is `s_tex` at slot 0. Additional textures occupy slots 1 onward in descriptor order. `u_material_rect` is supplied per draw. Scalars/vectors follow core's parameter packing; shader code must use the corresponding BGFX-compatible uniform declarations. There is no custom vertex shader option.

```zig
const materials = @import("materials");
// Preferred engine API: use catalog-backed engine texture bindings.
try game.createShaderMaterial(entity, .{
    .label = materials.fog.label,
    .shaders = materials.fog.shaders,
    .parameters = &materials.fog.parameters,
    .blend = materials.fog.blend,
    // .textures = caller's engine.ShaderTextureBinding slice
});
```

### Texture bindings are catalog `.image` entries only

The engine resolves a `.catalog` binding through the AssetCatalog and rejects
any entry whose `loader_kind` is not `.image` with `error.InvalidTexture`
(`labelle-engine/src/game/shader_material_mixin.zig`). **An atlas frame is not
an image entry**, so a mask/lookup texture a fragment shader samples must be
declared as a STANDALONE `.{ .name = ..., .image = "..." }` resource in
`project.labelle`, not packed into a sprite atlas. The generic material path
carries the same constraint the retired built-in water effect had; budget the
extra standalone PNGs when migrating.

A binding that is registered but not yet resident returns `error.TextureNotReady`
(streaming) or `error.AssetLoadFailed`; retry, do not treat either as fatal.
Textures are sampled in the sprite's own UV space, so a mask normally spans
exactly the logical rectangle it describes.

The module imports the same `labelle-core` instance as the game. It is wired into ordinary and promoted scripts, pack modules, executables, and test roots. It has no backend imports. For lower-level use, `var bindings = materials.fog.textures; bindings[0].texture = backend_id; const d = materials.fog.descriptor(&bindings);` returns a **borrowed** core descriptor; retain the caller's array through creation. The engine uses a distinct texture union for catalog pinning, so compose its descriptor from the exported fields instead of passing the core helper result.

| Variant | shaderc platform | profile |
|---|---|---|
| spv | linux | spirv |
| glsl | linux | 120 |
| essl | android | 300_es |
| mtl | osx | metal |
| dx11 | windows | s_5_0 |

Every requested variant is compiled with `--type fragment -O 3`. Desktop Windows/Linux require `spv` for the initial Vulkan path; Apple targets require `mtl`; Android/web require `essl`. Absent variants remain empty; no silent fallback or old binary reuse occurs on compilation failure. DX11 is schema/build supported but requires the pinned compiler's DirectX runtime support; it is not part of the four-variant acceptance fixture.

Generated `build.zig.zon` adds a separate hash-pinned `material_shaderc` host dependency; framework release pins are unchanged. The host compiler is built automatically by Zig. Set `LABELLE_SHADERC` or `-Dshaderc=<absolute executable>` to reuse a compatible host compiler. The pinned package's `shaders/` includes are always used, even with an executable override. Cross-target games still execute the host tool.

Shader source paths and literal include paths cannot contain parent traversal, absolute paths, Windows drives/backslashes, or NUL. Macro-based include names and symlinks within the source tree are rejected. Includes may use material-local files or the shared tree, e.g. `#include <shared/lamp_footprint.sc>` from `materials/shared/lamp_footprint.sc`. Keep image assets in `assets/`; material source files are limited to 1 MiB each. All material files plus pinned shader headers are tracked for compilation cache invalidation, conservatively rebuilding all variants on any material-tree edit. Compiler executable/artifact, arguments, source, fixed varyings and includes participate in Zig caching. Outputs live in Zig's cache, never the source tree. Adding/removing descriptor folders requires regeneration; edits to existing descriptors are embedded build inputs and need only `zig build`.

Verification: `zig build test-materials`; real compiler and generated-source coverage: `zig build test-material-integration -Dshaderc=<exe> -Dmaterial-test-core=<core checkout> -Dmaterial-test-zbgfx=<pinned zbgfx directory>`. The integration step checks all four variants, descriptor compilation against real core, cache hits, include edits, compiler failures, escaping includes, duplicate registrations, and missing required variants.
